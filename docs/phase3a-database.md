# Phase 3A Database Foundation

## Database architecture

The production database is PostgreSQL on Neon. SQLAlchemy 2.x and psycopg 3 are isolated in `services/persistence`; domain and API code depend on repository Protocols in `packages/ports`. Schema changes are owned by Alembic revisions under `migrations/versions`. PostgreSQL's `vector` extension stores embeddings in the same database; no ANN index or fixed embedding dimension is configured.

The initial migration creates `profiles`, `goals`, `constraints`, `commitments`, `scenarios`, `scenario_versions`, `scenario_branches`, `assumptions`, `research_queries`, `research_sources`, `evidence`, `runs`, `memories`, `embeddings`, `files`, `documents`, and `document_chunks`. File rows are metadata only; a file is not automatically a memory.

## Migration commands

Set `DATABASE_URL` to a `postgresql+psycopg://` connection URL, then run:

```sh
uv sync
uv run alembic upgrade head
uv run alembic downgrade -1
uv run alembic upgrade head
```

Application UUIDs are generated by the persistence models. Financial values use `NUMERIC`, timestamps use `TIMESTAMPTZ`, and domain snapshots use `JSONB`. Migrations, not ORM metadata creation, create production tables.

## Local database commands

```sh
docker compose -f docker-compose.db.yml up -d
export DATABASE_URL=postgresql+psycopg://life_sandbox:local_dev_only_change_me@localhost:55432/life_sandbox_dev
uv run alembic upgrade head
TEST_DATABASE_URL="$DATABASE_URL" uv run pytest -q tests/integration/persistence
docker compose -f docker-compose.db.yml down -v
```

The Compose database is for local migration and integration tests only. It uses a development-only local password and is not a production provider configuration.

## Environment variables

- `DATABASE_URL`: PostgreSQL `postgresql+psycopg://` URL; required only when opening the database.
- `DB_POOL_SIZE`: connection pool size, default `5`.
- `DB_MAX_OVERFLOW`: overflow connections, default `10`.
- `DB_POOL_TIMEOUT`: seconds to wait for a connection, default `30`.
- `DB_ECHO`: SQLAlchemy SQL logging, default `false`.

The engine and session factory are cached centrally. Importing or running the Phase 1 simulator does not require `DATABASE_URL`.

## Repository pattern

Application-facing interfaces live in `packages/ports/repositories.py`; SQLAlchemy adapters live in `services/persistence/repositories`. A `SqlAlchemyUnitOfWork` begins, commits, or rolls back one transaction and exposes the repositories for that transaction. Use it as a context manager. Repositories return plain mappings rather than ORM entities. Scenario versions persist both domain input snapshots; branches persist only parent links and deltas.

## Ownership and RLS

The trusted `AuthPrincipal` contains the internal UUID, auth subject, and provider. `AuthProvider` is a Protocol; tests use `FakeAuthProvider`. Repository methods for user-owned rows require `user_id` and filter reads, lists, updates, and deletes by it. Relationship repositories first verify the parent belongs to that user. Do not treat a request-body UUID as identity.

The UnitOfWork sets transaction-local PostgreSQL `app.user_id` before repository operations. The migration enables RLS on application-owned tables and adds policies comparing `user_id` (or the owning parent row) with that setting. The managed auth schema is not touched. A production authentication adapter is not included in Phase 3A.

Use a non-superuser runtime database role without `BYPASSRLS`; PostgreSQL superusers bypass row policies. Keep migration credentials separate from application credentials in deployment configuration.
